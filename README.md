# DialectSql

`braesident/dialectsql` erzeugt SQL für MySQL, MariaDB, Microsoft SQL Server und PostgreSQL. Enthalten sind `SqlBuilder`, `SelectBuilder`, `WhereBuilder` und `SqlRenderer` im Namespace `Braesident\DialectSql`. Es besteht keine Pflichtabhängigkeit auf CipherPDO oder DbMigration.

Die [SQL-Funktionsmatrix und Projektliste](SQL_FEATURES.md) zeigt für alle drei Dialekte, welche Befehle, Klauseln, Funktionen und Datentypen umgesetzt sind, wie sie angewendet werden und wo eine gemeinsame Umsetzung fehlt. Entwicklungsrichtlinien stehen in [CONCEPT.md](CONCEPT.md).

## PostgreSQL und gemeinsame Paginierung

Als Dialekt `pgsql` verwenden; `postgres` und `postgresql` sind ebenfalls zulässig. `SqlRenderer` erkennt PDO-Verbindungen mit dem Treiber `pgsql` automatisch. SQL-Erzeugung mit den statischen Buildern benötigt keine Verbindung und keinen installierten PostgreSQL-PDO-Treiber. Für die spätere Ausführung über PDO wird `pdo_pgsql` benötigt.

```php
$query = [
  'select' => '*',
  'from' => 'products',
  'order_by' => 'id',
  'limit' => 10,
  'offset' => 20,
];
$sql = SelectBuilder::build($query, 'pgsql');
// SELECT * FROM "products" ORDER BY id LIMIT 10 OFFSET 20
```

Dasselbe Objekt erzeugt bei MySQL `LIMIT 20, 10` und bei SQL Server `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY`. SQL Server verwendet bei SELECT für `limit:0` ein `TOP (0)`, sonst OFFSET/FETCH. Bei UPDATE/DELETE wird `limit` zu `TOP (n)`; PostgreSQL lehnt ein direktes DML-`limit` ab. MySQL-Joins mit DML-Limit werden ausdrücklich abgelehnt. Details stehen in der [Limit-/TOP-Gegenüberstellung](SQL_FEATURES.md#2-zeilenbegrenzung-ein-objekt-verschiedene-syntax).

PostgreSQL unterstützt die vorhandenen Definitionen für Tabellen, Spaltenänderungen, Indizes, Constraints, Views sowie INSERT/UPDATE/DELETE. Beispiele:

```php
$statements = SqlBuilder::build([
  'type' => 'create_table',
  'schema' => 'shop',
  'table' => 'products',
  'columns' => [
    ['name' => 'id', 'type' => 'int', 'autoIncrement' => true],
    ['name' => 'active', 'type' => 'boolean', 'nullable' => false, 'default' => true],
    ['name' => 'data', 'type' => 'jsonb', 'comment' => 'Produktdaten'],
  ],
  'primaryKey' => ['id'],
], 'pgsql');
// CREATE TABLE und COMMENT ON COLUMN als getrennte Statements.
```

- PostgreSQL-Identity verwendet `GENERATED BY DEFAULT AS IDENTITY` und benötigt PostgreSQL 10 oder neuer. Zusätzliches `default` oder `nullable:true` ist dabei unzulässig.
- Ohne `schema` bleibt die Tabelle unqualifiziert und folgt dem Suchpfad der Verbindung. Es wird kein `dbo` ergänzt. Bei SELECT das Schema innerhalb von `from` oder als `schema.table` angeben.
- Bei Großschreibung in Spaltennamen `['col' => 'p.ProductId']` verwenden; PostgreSQL erhält dann `"p"."ProductId"`. Stringausdrücke bleiben ausdrücklich SQL-Ausdrücke.
- `join` bei UPDATE wird in `FROM`, bei DELETE in `USING` übersetzt. Die Übersetzung unterstützt innere Joins. Äußere DML-Joins werden abgelehnt.
- PostgreSQL hat kein Spalten-`UNSIGNED`, `ON UPDATE CURRENT_TIMESTAMP` oder `FIRST`/`AFTER`; entsprechende Optionen werden abgelehnt. `enum` wird als VARCHAR mit CHECK erzeugt.
- Zum Entfernen von PostgreSQL-Indizes/Constraints einen Namen angeben. `drop_default` verwendet `columns`. `modify_column` ändert nur angegebene Eigenschaften; Enum-/Identity-Änderungen und Typkonvertierungen mit USING benötigen Raw-SQL.
- PostgreSQL-Trigger benötigen `function` mit dem Namen einer bestehenden Triggerfunktion, optional `functionArgs`. Ein Inline-`body` kann nicht automatisch übertragen werden. `drop_trigger` benötigt zusätzlich `table`. [Triggerbeispiel und Grenzen](SQL_FEATURES.md#6-views-trigger-und-programmierbare-objekte).
- Dialekt-Maps unterstützen `pgsql`, `postgres` und `postgresql`, beispielsweise `['mysql' => 'SELECT NOW()', 'sqlsrv' => 'SELECT SYSDATETIME()', 'pgsql' => 'SELECT CURRENT_TIMESTAMP']`.

Nach Veröffentlichung: `composer require braesident/dialectsql:^1.0`. Lokal kann ein Composer-Repository vom Typ `path` verwendet werden. Dieses Projekt ist noch nicht veröffentlicht.

## Verwendung ohne Migrationen

```php
use Braesident\DialectSql\SqlBuilder;
use Braesident\DialectSql\SqlRenderer;

$sql = SqlBuilder::build([
  'type' => 'update', 'table' => 'config',
  'set' => ['cValue' => ['raw' => ':value']],
  'where' => ['cIdentifier', '=', ['raw' => ':id']],
], 'mysql');

// PDO oder CipherPDO; der Renderer öffnet selbst keine Verbindung.
$renderer = new SqlRenderer($pdo);
$stmt = $pdo->prepare($renderer->render(['select' => '*', 'from' => 'config']));
$stmt->execute();
```

`SqlBuilder` und `SelectBuilder` können SQL ohne Verbindung erzeugen. `SqlRenderer` ermittelt Dialekt und Serverkontext über eine übergebene PDO-Verbindung. `renderAll()` liefert eine flache Liste von SQL-Strings. Parameterwerte werden durch die Anwendung an PDO gebunden.

## Optionale DbMigration-Integration ab 1.1.0

```php
$renderer = new SqlRenderer($pdo);
$manager = new \Braesident\DbMigration\MigrationManager(
  $pdo, $migrationPath, $migrationNamespace,
  renderer: [$renderer, 'renderAll']
);
$manager->migrate();

// Für JSON-Schritte, die direkt ausgeführt werden, etwa in Extensions:
$migration = new \Braesident\DbMigration\Migration(
  $pdo, renderer: [$renderer, 'renderAll']
);
$migration->execute($step);
```

Bestehende JSON-Schritte behalten `"builder": "sql"`, `up`/`down`, Dialektfilter und ihre Inhalte. `src/definition.schema.json` beschreibt eigenständige Builder-Definitionen. Der bisherige Migrations-Schema-Pfad verbleibt in DbMigration; historische JSON-Dateien müssen nicht geändert werden.

Die alten Builder-/Renderer-Klassen unter `Braesident\DbMigration` sind ab DbMigration 1.1.0 deprecated und werden in DbMigration 2.0.0 entfernt. `Migration`, `MigrationManager` und das JSON-Migrationsformat bleiben bestehen.

## Eingabeprüfung, Bezeichner und Parameter

Unbekannte SELECT-/Builder-/Spaltenfelder, negative oder gebrochene Limits und unbekannte Dialekte führen zu `InvalidArgumentException`. Ganze numerische Strings wie `"10"` bleiben bei Limits/Offsets zulässig. Nicht unterstützte Angaben werden ausdrücklich abgelehnt, etwa SQL-Server-`JOIN USING`, `unsigned`/`onUpdate` bei SQL-Server-Spalten und MySQL-DML-Joins mit `limit`.

`col` quotet Bezeichner in allen Dialekten. Strings in SELECT-Ausdrücken bleiben SQL; `value` bezeichnet ein Literal, `param` einen geprüften benannten PDO-Platzhalter:

```php
$query = [
  'select' => [['col' => 'p.ProductId']],
  'from' => ['table' => 'products', 'as' => 'p'],
  'where' => [['col' => 'p.ProductId'], '=', ['param' => 'id']],
];
$sql = SelectBuilder::build($query, 'pgsql');
// SELECT "p"."ProductId" FROM "products" AS "p" WHERE "p"."ProductId" = :id
$stmt = $pdo->prepare($sql);
$stmt->execute(['id' => 42]);
```

`SelectBuilder::param('id')` liefert dieselbe Ausdrucksstruktur. Der Renderer bindet weiterhin keine Werte. SQL-Server-Textliterale erhalten ein N-Präfix für Unicode. Backslashes in MySQL-Literalen werden über `CONVERT(X'...' USING utf8mb4)` erhalten; PostgreSQL verwendet dafür E-Literale.

Leeres `IN []` ergibt `1=0`, leeres `NOT IN []` ergibt `1=1`. Auch `WhereBuilder::andIn()`/`orIn()` entfernen leere Listen nicht mehr; leere Strings und NULL bleiben als übergebene Werte erhalten. Soll ein optionaler Filter bei leerer Benutzerauswahl entfallen, entscheidet dies die Anwendung vor dem Builder-Aufruf. Explizite Vergleiche `= null`/`<> null`, auch mit `value:null`, werden zu IS NULL/IS NOT NULL.

## SELECT-CTEs und globale UNION-Paginierung

```php
$query = [
  'with' => [[
    'name' => 'active_products',
    'columns' => ['id'],
    'query' => ['select' => 'id', 'from' => 'products', 'where' => ['active', '=', true]],
  ]],
  'select' => 'id',
  'from' => 'active_products',
];
$sql = SelectBuilder::build($query, 'pgsql');
```

Die gleiche Definition funktioniert für SQL Server und MySQL ab Version 8; ältere MySQL-Versionen werden bei vorhandenen Versionsinformationen abgelehnt. Rekursive SELECT-CTEs setzen `recursive:true`. MySQL/PostgreSQL erhalten WITH RECURSIVE, SQL Server WITH. Fluent: `with($name, $query, $columns = [], $recursive = false)`.

Die CTE-API beschreibt SELECT-CTEs. Ein WITH vor DML benötigt weiterhin explizites SQL; SQL-Server-INSERT-SELECT mit CTE sowie verschachteltes WITH werden abgelehnt. SQL-Server-Anwendungen müssen beim Einfügen in einen größeren Batch das vorherige Statement mit Semikolon beenden. Rekursionsgrenzen und erlaubte rekursive Ausdrücke bleiben serverabhängig.

Für die gesamte UNION-Ergebnismenge gibt es `union_order_by`, `union_limit` und `union_offset` (auch camelCase). Die bestehenden `order_by`/`limit`/`offset` gelten weiterhin für die erste Teilabfrage:

```php
$query = [
  'select' => 'id', 'from' => 'products',
  'union_all' => [['select' => 'id', 'from' => 'archive']],
  'union_order_by' => [['expr' => 'id', 'dir' => 'DESC']],
  'union_limit' => 10, 'union_offset' => 20,
];
```

Der Builder erzeugt eine äußere SELECT-Abfrage über das UNION. Fluent: `unionOrderBy('id', 'DESC')->unionLimit(10, 20)`. Die UNION-Ausgabespalten müssen für diese äußere Abfrage eindeutig benannt sein.

## DML-Rückgaben mit RETURNING / OUTPUT

```php
$definition = [
  'type' => 'insert', 'table' => 'products',
  'values' => [['name' => 'Öl']],
  'returning' => ['id', ['col' => 'name', 'as' => 'label']],
];
$sql = SqlBuilder::build($definition, 'pgsql');
// INSERT INTO "products" ("name") VALUES ('Öl') RETURNING "id", "name" AS "label"
$sql = SqlBuilder::build($definition, 'sqlsrv');
// INSERT INTO [dbo].[products] ([name]) OUTPUT INSERTED.[id], INSERTED.[name] AS [label] VALUES (N'Öl')
```

`returning` gilt auch für UPDATE, DELETE und Upserts. Erlaubt sind eine nicht leere Liste unqualifizierter Zielspalten, optionale Spaltenaliase oder `"*"`. INSERT/UPDATE/Upsert liefern den neuen, DELETE den entfernten Zustand; SQL Server nutzt INSERTED beziehungsweise DELETED. MySQL lehnt die Option ab. Rückgabeausdrücke, OUTPUT INTO, alte und neue Werte gemeinsam sowie eine automatische MySQL-Emulation sind nicht enthalten. SQL-Server-OUTPUT ohne INTO unterliegt insbesondere Einschränkungen bei aktivierten Triggern; Werte werden vor nachgelagerten Triggeränderungen zurückgegeben. Bei Fehlern oder Rollback sind Rückgaben nicht als bestätigte Speicherung zu verwenden.

## Upsert: Einfügen oder Aktualisieren

Mit derselben Definition wird eine neue Zeile eingefügt oder bei einem passenden Schlüssel die vorhandene Zeile aktualisiert. Sie kann unmittelbar an `SqlBuilder`/`SqlRenderer` oder als Builder-Schritt übergeben werden:

```json
{
  "type": "upsert",
  "table": "products",
  "conflictColumns": ["sku"],
  "values": [
    {"sku": "A-100", "name": "Öl", "stock": 5}
  ],
  "set": {
    "name": {"incoming": "name"},
    "stock": {"op": "+", "left": {"col": "stock"}, "right": {"incoming": "stock"}}
  },
  "mysqlConflict": "any_unique"
}
```

Die Tabelle muss bereits einen passenden PRIMARY KEY oder UNIQUE-Schlüssel auf `sku` besitzen. Bei neuen Produkten wird `stock=5` eingefügt. Bei vorhandenen Produkten werden Name und Bestand aktualisiert; der Bestand wird dabei um 5 erhöht.

```php
$definition = [
  'type' => 'upsert',
  'table' => 'products',
  'conflictColumns' => ['sku'],
  'values' => [['sku' => ['param' => 'sku'], 'name' => ['param' => 'name'], 'stock' => ['param' => 'stock']]],
  'set' => [
    'name' => SelectBuilder::incoming('name'),
    'stock' => SelectBuilder::calc(SelectBuilder::col('stock'), '+', SelectBuilder::incoming('stock')),
  ],
  'mysqlConflict' => 'any_unique',
];
$sql = SqlBuilder::build($definition, 'pgsql'); // Ebenso mysql oder sqlsrv.
$stmt = $pdo->prepare($sql);
$stmt->bindValue(':sku', 'A-100', PDO::PARAM_STR);
$stmt->bindValue(':name', 'Öl', PDO::PARAM_STR);
$stmt->bindValue(':stock', 5, PDO::PARAM_INT);
$stmt->execute();
```

| Feld / Ausdruck | Bedeutung |
| --- | --- |
| `values` oder `rows` | Eingabezeilen wie bei INSERT; eine oder mehrere Objektzeilen, alternativ positionale Werte mit `columns`. Beide Felder gleichzeitig sind unzulässig. |
| `conflictColumns` | Nicht leere Liste der Schlüsselspalten, auch zusammengesetzt wie `["tenant", "sku"]`. Alle müssen in jeder Eingabezeile vorkommen. |
| `set` | Nicht leeres Objekt oder bestehende UPDATE-Zuweisungsliste; bestimmt ausschließlich die Änderungen an vorhandenen Zeilen. Neue Zeilen erhalten die Eingabewerte. |
| `{"incoming":"stock"}` | Der neu angelieferte Wert der angegebenen Eingabespalte. Nur im Upsert-SET gültig, auch verschachtelt in Ausdrücken, Funktionen oder CASE. |
| `{"col":"stock"}` im Upsert-SET | Der bisherige Wert der Zielspalte; ohne Tabellenqualifizierung angeben. |
| String, Zahl, boolean, NULL in `set` | Literal wie bei UPDATE. Für Platzhalter `param`, für bewusst natives SQL `raw` verwenden. |
| `mysqlConflict:"any_unique"` | Erforderliche ausdrückliche Wahl des MySQL-/MariaDB-Verhaltens; in einer gemeinsamen Definition für alle drei Dialekte verwendbar. |
| `returning` | Optionale Zielspalten-Rückgabe für PostgreSQL und SQL Server wie bei anderen DML-Definitionen. MySQL lehnt sie ab. |

| Dialekt | Erzeugte Syntax | Konfliktverhalten |
| --- | --- | --- |
| MySQL / MariaDB | INSERT ... ON DUPLICATE KEY UPDATE | Jeder PRIMARY-/UNIQUE-Konflikt kann das Update auslösen; die Datenbank kann `conflictColumns` nicht als ausgewähltes Konfliktziel erzwingen. |
| PostgreSQL | INSERT ... ON CONFLICT (...) DO UPDATE | Verwendet die angegebenen Konfliktspalten. Ein Konflikt mit einem anderen UNIQUE-Schlüssel bleibt ein Fehler. |
| SQL Server | MERGE ... WITH (HOLDLOCK) | Vergleicht die angegebenen Schlüssel und erzeugt nur WHEN MATCHED UPDATE sowie WHEN NOT MATCHED INSERT. Andere UNIQUE-Konflikte bleiben Fehler. |

MySQL benötigt deshalb `mysqlConflict:"any_unique"`. Ohne diese Angabe wird das Upsert abgelehnt. Bei mehreren UNIQUE-Schlüsseln muss die Anwendung die mögliche Auswahl einer anderen vorhandenen Zeile berücksichtigen; eine Gleichsetzung mit dem engeren PostgreSQL-/SQL-Server-Konfliktziel erfolgt nicht. [MySQL-Konfliktregeln](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html).

Ohne MySQL-Versionskontext wird die Zeilenalias-Syntax ab MySQL 8.0.19 erzeugt. `SqlRenderer` erkennt Serverprodukt und Version über PDO. Für bekannte ältere MySQL-Versionen und MariaDB wird `VALUES(column)` verwendet; direkt beispielsweise `SqlBuilder::build($definition, ['dialect' => 'mysql', 'serverVersionId' => 50744])`. In neueren MySQL-Versionen vermeidet der Zeilenalias die veraltete VALUES-Funktion. [MySQL-Versionen](https://dev.mysql.com/doc/refman/8.0/en/insert-on-duplicate.html), [MariaDB VALUES](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/inserting-loading-data/insert-on-duplicate-key-update).

Ein Upsert erzeugt genau ein SQL-Statement. Es wird keine vorherige SELECT-/UPDATE-/INSERT-Abfolge ausgeführt und keine Transaktion durch die Bibliothek gestartet. SQL Server erhält HOLDLOCK für die MERGE-Zieltabelle; Transaktionsgrenzen und die Behandlung von Sperrkonflikten bleiben bei der Anwendung. Rückgaben haben keine garantierte Reihenfolge, und betroffene Zeilenzahlen werden nicht dialektübergreifend vereinheitlicht. [SQL Server MERGE](https://learn.microsoft.com/en-us/sql/t-sql/statements/merge-transact-sql?view=sql-server-ver17), [PostgreSQL ON CONFLICT](https://www.postgresql.org/docs/18/sql-insert.html).

Konfliktschlüssel müssen nicht NULL und innerhalb der Eingabe eindeutig sein. Bekannte NULL-Literale und identische literale Schlüsseltupel werden abgelehnt. Bei Parametern, Ausdrücken, Typkonvertierungen und Kollationen muss die Anwendung die Eindeutigkeit sicherstellen. Automatisch erzeugte IDs und andere Standardspalten weglassen. DEFAULT in Eingabezellen oder SET, Schlüsseländerungen, leeres SET als DO NOTHING, INSERT-SELECT-Upserts, strukturierte SET-Unterabfragen, Konfliktbedingungen/Indexausdrücke und allgemeine MERGE-Synchronisierung sind nicht Teil dieser API. Bewusstes natives SQL bleibt über `raw` möglich.

## JSON-Format (Kurzübersicht)

- Datei: `MigrationYYYYMMDDHHMMSS.json`
- Felder: `up` und `down` (jeweils Liste von Steps)
- Step:
  - Builder-Step: `{ "builder": "sql", "definition": { ... } }`
  - Dialekt-SQL: `{ "mysql": "...", "sqlsrv": "...", "sql": "...", "default": "..." }`
  - Optional: `only`/`exclude` (oder `dialects`/`include`) begrenzen Steps auf Dialekte, z.B. `{ "only": ["sqlsrv"] }`

## PHP-Notation (Migration vs. Quellcode)

- Migrationen: `$this->execute([...])` akzeptiert Arrays oder `(object)[...]` (JSON-ähnlich).
- Quellcode: mit `SqlRenderer` nutzt du dieselbe Definition ohne Wrapper.

Beispiel Migration:
```php
$this->execute([
  'builder' => 'sql',
  'definition' => [
    'type' => 'insert',
    'table' => 'config',
    'values' => [['cIdentifier' => 'orderid_pad_sign', 'cDefault' => '0']]
  ]
]);
```

Beispiel Quellcode:
```php
$sql = $renderer->render([
  'type' => 'insert',
  'table' => 'config',
  'values' => [['cIdentifier' => 'orderid_pad_sign', 'cDefault' => '0']]
]);
```

## Builder-Definitionen

- `create_table`: Tabelle erzeugen (Spalten, PK, Unique, Indexe, FKs, Checks; optional `comment` pro Spalte)
- `drop_table`: Tabelle löschen
- `alter_table`: Tabelle verändern (Actions, siehe unten)
- `create_view`: View erzeugen/ersetzen
- `drop_view`: View löschen
- `create_trigger`: Trigger erstellen
- `alter_trigger`: Trigger ändern (mysql: DROP + CREATE)
- `drop_trigger`: Trigger entfernen
- `insert`: INSERT (VALUES oder INSERT...SELECT)
- `upsert`: INSERT oder UPDATE bei Schlüsselkonflikt (VALUES, conflictColumns, set)
- `update`: UPDATE (SET + WHERE)
- `delete`: DELETE (optional JOINs, WHERE, LIMIT)
- `raw`: Dialekt-SQL direkt

## alter_table Actions

- `add_column`: Spalte hinzufügen (optional: `after`, `first` für mysql)
- `modify_column`: Spalte ändern (sqlsrv ohne default/onUpdate/identity)
- `drop_column`: Spalte entfernen
- `rename_column`: Spalte umbenennen
- `rename_table`: Tabelle umbenennen
- `add_index` / `drop_index`: Index hinzufügen/entfernen
- `add_unique` / `drop_unique`: Unique-Constraint hinzufügen/entfernen
- `drop_default`: Default-Constraint entfernen (sqlsrv: per Constraint oder Spaltenliste)
- `add_check` / `drop_check`: Check-Constraint hinzufügen/entfernen
- `add_primary_key` / `drop_primary_key`: Primary Key hinzufügen/entfernen
- `add_foreign_key` / `drop_foreign_key`: Foreign Key hinzufügen/entfernen

Hinweise:
- mysql: `rename_table` nutzt `RENAME TABLE`, sqlsrv nutzt `sp_rename`.
- sqlsrv: `drop_primary_key` benötigt den Constraint-Namen.
- mysql: Foreign-Key-Namen werden vergeben; wenn kein `name` gesetzt ist, erzeugt MySQL automatische Namen (z. B. `table_ibfk_1`). Zum Droppen wird trotzdem der Name benötigt.
- mysql: `drop_foreign_key` kann optional `columns`/`refTable` nutzen und ermittelt die Namen via `information_schema` (läuft als mehrere Statements mit `PREPARE`).
- mysql/sqlsrv: `drop_unique`/`drop_index` können alternativ `columns` nutzen, wenn der Name unbekannt ist (Lookup über Katalogtabellen).
- sqlsrv: `drop_default` kann `columns` nutzen und entfernt Default-Constraints per sys.default_constraints.
- sqlsrv: `drop_foreign_key` kann `columns` und/oder `refTable` nutzen, wenn der Name unbekannt ist.
- Views: `create_view` nutzt in mysql `CREATE OR REPLACE VIEW`. In sqlsrv wird bei `replace=true` zuerst eine Dummy-View erzeugt und dann `ALTER VIEW` genutzt.
- Views: `select` kann ein String, ein String-Array oder ein Dialekt-Map sein (z.B. `{ "mysql": [...], "sqlsrv": [...] }`).
- Views: Alternativ kann `query` verwendet werden (JSON-Query-Builder). Dann wird der SELECT aus der Struktur gebaut.
- Trigger: `body` kann ein String, String-Array, Dialekt-Map oder Builder-Definition(en) sein (z.B. `insert`/`update`/`delete`).
- Trigger: `timing` kann dialektspezifisch sein (z.B. `{ "mysql": "before", "sqlsrv": "instead of" }`).

Beispiel (Default-Constraint entfernen, sqlsrv):
```json
{
  "builder": "sql",
  "definition": {
    "type": "alter_table",
    "table": "account",
    "schema": "dbo",
    "actions": [
      { "action": "drop_default", "columns": ["cShort", "kVehicle_storage"] },
      { "action": "drop_column", "name": "kVehicle_storage" }
    ]
  }
}
```

Beispiel (Foreign Key ohne Namen entfernen, sqlsrv):
```json
{
  "builder": "sql",
  "definition": {
    "type": "alter_table",
    "table": "storage_unit",
    "schema": "dbo",
    "actions": [
      { "action": "drop_foreign_key", "refTable": "vehicle_storage" }
    ]
  }
}
```

## Datentypen (Hinweise)

- `tinyblob` wird in sqlsrv zu `VARBINARY(255)`.
- `blob`/`mediumblob`/`longblob` werden in sqlsrv zu `VARBINARY(MAX)` (max. 2 GB; MySQL `LONGBLOB` kann bis 4 GB).

## insert

Unterstützt:
- `INSERT ... VALUES` (eine oder mehrere Zeilen)
- `INSERT ... SELECT` (über `select` als SQL oder `query` als AST)

Hinweis (dialekt-neutral):
- Für AUTO_INCREMENT/IDENTITY-Spalten besser die Spalte weglassen oder `DEFAULT` verwenden (SQL Server akzeptiert `NULL` bei IDENTITY nicht).

VALUES (mehrere Zeilen):
```json
{
  "builder": "sql",
  "definition": {
    "type": "insert",
    "table": "config",
    "columns": ["cIdentifier", "cDefault", "cValue"],
    "values": [
      ["orderid_pad_sign", "0", null],
      ["orderid_pad_count", "0", null],
      ["customerid_pad_sign", "0", null],
      ["customerid_pad_count", "0", null]
    ]
  }
}
```

PHP (Migration):
```php
$this->execute([
  'builder' => 'sql',
```

## update

Unterstützt:
- `UPDATE ... SET ... WHERE ...` (optional: `limit` / sqlsrv: `TOP`)
- Join-Updates über `join`/`left_join`/`right_join` (MySQL: `UPDATE ... JOIN ...`, SQL Server: `UPDATE ... FROM ... JOIN ...`)

Hinweis:
- Strings in `set` sind immer Literale. Für Spalten/Expressions nutze z.B. `{ "col": "o.kOrder" }`, `{ "raw": "o.kOrder" }` oder Expr-Objekte (`op`, `fn`, `case`, ...).

SET als Objekt (Spalte => Wert):
```json
{
  "builder": "sql",
  "definition": {
    "type": "update",
    "table": "config",
    "set": {
      "cValue": "1"
    },
    "where": {
      "cIdentifier": "orderid_pad_sign"
    }
  }
}
```

## SqlRenderer

Für normale Projekt‑Queries (außerhalb von Migrationen). Rendert SQL aus Builder‑Definitionen, Dialekt‑Maps oder SELECT‑ASTs.

Minimal:
```php
use Braesident\DialectSql\SqlRenderer;

$renderer = new SqlRenderer($pdo);
$sql = $renderer->render([
  'select' => ['*'],
  'from' => 'extensions',
  'where' => ['eStatus', '=', ['raw' => ':status']]
]);
```

Mit Schema (SQL Server):
```php
$sql = $renderer->render([
  'select' => ['*'],
  'from' => ['schema' => 'dbo', 'table' => 'view_account']
]);
```

Mehrere Statements (z. B. Trigger/Kommentare):
```php
$statements = $renderer->renderAll($definition);
foreach ($statements as $sql) {
  $stmt = $pdo->prepare($sql);
  $stmt->execute($params);
}
```

Dialekt‑Map (raw SQL):
```php
$sql = $renderer->render([
  'mysql' => 'SELECT NOW()',
  'sqlsrv' => 'SELECT SYSDATETIME()'
]);
```

Schema‑Hinweis (SQL Server):
- Builder‑Definitionen (z. B. `create_table`, `create_view`, `insert`, `update`, `delete`) unterstützen `schema` direkt am Root.
- SELECT‑ASTs lesen `schema` nicht am Root. Nutze stattdessen:
  - `from: ['table' => 'view_account', 'schema' => 'dbo']`
  - oder `from: 'dbo.view_account'`

WhereBuilder (kompakte WHERE + Params):
```php
use Braesident\DialectSql\WhereBuilder;

$where = new WhereBuilder();
$where->andNotEquals('o.eStatus', 'deleted');
$where->andParam('o.kAccount', '=', (int) $accountId, 'kaccount');
$where->andIn('o.eStatus', $statusFilter, 'status');
$where->orIn('o.eStatus', $fallbackFilter, 'status_fallback');

$objTotals['where'] = $where->conditions();
$params = $where->params();
```

Weitere Helper (Vergleiche + Kurzformen):
```php
$where->andLt('o.nTotal', 10);
$where->orGte('o.nTotal', 100);
$where->andLtParam('o.nTotal', 10, 'min_total');
$where->andGteParam('o.nTotal', 100, 'max_total');
```

Gruppierung:
```php
$where = new WhereBuilder();
$where->andEquals('a', 1)
      ->andEquals('b', 2)
      ->orEquals('c', 3)
      ->orGroup([
        ['d', '=', 4],
        ['e', '=', 5]
      ]);
```

Builder‑Definition:
```php
$sql = $renderer->render([
  'type' => 'update',
  'table' => 'extensions',
  'set' => ['eStatus' => ['raw' => ':status']],
  'where' => ['kExtension', '=', ['raw' => ':id']]
]);
```

## SelectBuilder (Kurzform)

JSON (query-basierter View):
```json
{
  "builder": "sql",
  "definition": {
    "type": "create_view",
    "view": "view_material_product",
    "replace": true,
    "query": {
      "select": [
        "mp.*",
        { "expr": { "op": "+", "left": "mp.nStock", "right": { "fn": "ifnull", "args": [ { "fn": "sum", "args": ["su.nQuantity"] }, 0 ] } }, "as": "nTotal_stock" },
        { "col": "mc.cName", "as": "cOrigin" }
      ],
      "from": { "table": "material_product", "as": "mp" },
      "left_join": [
        { "table": "storage_unit", "as": "su", "on": ["mp.kMaterial_product", "=", "su.kProduct"] },
        { "table": "material_category", "as": "mc", "on": ["mc.kMaterial_category", "=", "mp.kCategory"] }
      ],
      "group_by": ["mp.kMaterial_product"]
    }
  }
}
```

PHP (Migration, Builder-Definition):
```php
$this->execute([
  'builder' => 'sql',
  'definition' => [
    'type' => 'create_view',
    'view' => 'view_material_product',
    'replace' => true,
    'query' => [
      'select' => [
        'mp.*',
        ['expr' => ['op' => '+', 'left' => 'mp.nStock', 'right' => ['fn' => 'ifnull', 'args' => [['fn' => 'sum', 'args' => ['su.nQuantity']], 0]]], 'as' => 'nTotal_stock'],
        ['col' => 'mc.cName', 'as' => 'cOrigin']
      ],
      'from' => ['table' => 'material_product', 'as' => 'mp'],
      'left_join' => [
        ['table' => 'storage_unit', 'as' => 'su', 'on' => ['mp.kMaterial_product', '=', 'su.kProduct']],
        ['table' => 'material_category', 'as' => 'mc', 'on' => ['mc.kMaterial_category', '=', 'mp.kCategory']]
      ],
      'group_by' => ['mp.kMaterial_product']
    ]
  ]
]);
```

PHP (fluent API):
```php
$sb = new SelectBuilder('mysql');
$sb->select('mp.*')
   ->select(SelectBuilder::calc('mp.nStock', '+', SelectBuilder::fn('ifnull', SelectBuilder::fn('sum', 'su.nQuantity'), 0)), 'nTotal_stock')
   ->select('mc.cName', 'cOrigin')
   ->from('material_product', 'mp')
   ->leftJoin('storage_unit', 'su', ['mp.kMaterial_product', '=', 'su.kProduct'])
   ->leftJoin('material_category', 'mc', ['mc.kMaterial_category', '=', 'mp.kCategory'])
   ->groupBy('mp.kMaterial_product');
$sql = $sb->statement();
```
